# 项目整体：Query改写

## 1. 项目简介

本项目是面向 RAG 检索系统的**双层 Query 智能重写工具**，基于阿里云通义千问 DashScope 大模型实现，分为两大独立模块：

1. **对话场景 Query 改写**：处理多轮对话模糊、省略、多意图、反问、对比类用户提问，用于本地知识库检索优化；
2. **联网检索 Query 预处理**：自动判断用户问题是否需要联网搜索，生成标准化检索词、关键词、搜索策略，用于实时互联网信息检索。

### 解决核心痛点

- 用户口语化、省略、指代模糊提问，向量检索召回率低；
- 多轮对话上下文丢失导致 Query 语义缺失；
- 实时时效性问题无法区分静态知识 / 联网信息；
- 原生提问不适合搜索引擎，缺少关键词、时间、实体限定。

## 2. 整体架构与设计思路

### 分层架构

```
┌─────────────────────────────────────────────────────┐
│               底层通用LLM调用层 get_completion        │
│ 统一封装DashScope调用、异常捕获、兼容无库本地模拟    │
└───────────────────────┬─────────────────────────────┘
                        ↓
┌──────────────┬────────┴──────────┐
│ 对话Query层   │      联网检索层   │
│ QueryRewriter │ WebSearchRewriter│
│ 知识库检索专用│ 互联网实时检索专用│
└──────────────┴──────────────────┘
```

### 整体设计思路

1. **解耦分层**：通用 LLM 调用逻辑抽离为公共函数，两个改写类独立互不干扰，可单独实例化使用；
2. **类型自动识别 + 专项改写**：先通过大模型识别 Query 类型，再调用对应专项改写 Prompt，兼顾通用性与改写精度；
3. **强结构化输出约束**：所有分析结果强制 JSON 格式返回，统一解析兜底逻辑，避免模型自由文本导致解析崩溃；
4. **全链路异常兜底**：API 调用失败、JSON 解析失败、库缺失均设置降级返回，保证业务流程不中断；
5. **场景分离**：区分「本地静态知识库检索」与「互联网实时联网检索」两套改写逻辑，各司其职。

## 3. 模块一：通用对话 Query 改写（QueryRewriter）

### 模块定位

针对**多轮对话场景、本地知识库检索**，修复用户口语化模糊提问，生成清晰、独立、无歧义检索 Query。

### 支持 5 大类 Query 专项改写

|             改写方法              |   适用场景   |                           功能说明                           |
| :-------------------------------: | :----------: | :----------------------------------------------------------: |
|  rewrite_context_dependent_query  | 上下文依赖型 | 补全省略词、承接上文，生成独立完整问题（例：“还有别的吗？”→补全前文园区） |
| rewrite_ambiguous_reference_query |  模糊指代型  |        消解 “它、这个、都” 等代词歧义，替换为明确实体        |
|     rewrite_comparative_query     |    对比型    |     提取对比对象，生成明确对比检索语句（例：哪个更好玩）     |
|    rewrite_multi_intent_query     |  多意图拆分  |      将复合问题拆分为独立子问题 JSON 数组，多轮分别检索      |
|     rewrite_rhetorical_query      |    反问型    |            转换反问 / 情绪问句为中立客观检索问题             |

### 核心自动调度入口

```
auto_rewrite_and_execute()
```

1. 调用`auto_rewrite_query`自动识别 Query 类型，输出分类、置信度、初步改写结果；
2. 根据识别类型自动匹配对应专项改写函数；
3. 返回整合结果：原始 query、识别类型、置信度、最终改写文本、原始识别 JSON。

### 输出字段结构

```json
{
    "original_query": "原始用户提问",
    "detected_type": "识别出的query类型",
    "confidence": 0~1浮点数,
    "rewritten_query": "最终改写完成的检索query",
    "auto_rewrite_result": "模型自动分类的完整JSON结果"
}
```

## 4. 模块二：联网检索 Query 预处理（WebSearchQueryRewriter）

### 模块定位

针对**时效性、实时动态信息**场景，自动判断是否需要调用互联网搜索，并生成标准化检索素材，配合搜索引擎使用。

### 三大核心方法流程

1. identify_web_search_needs () 联网需求识别

   定义 8 类必须联网的场景（时效 / 价格 / 营业 / 活动 / 天气 / 交通 / 预订 / 实时人流量），输出是否检索、原因、置信度 JSON。

2. rewrite_for_web_search () 搜索引擎 Query 优化

   标准化改写规则：补充地点 / 时间、去除口语、提取关键词、明确搜索意图，输出改写词、关键词数组、检索意图、推荐网站类型。

3. generate_search_strategy () 完整检索策略生成

   输出核心关键词、扩展同义词、推荐检索平台、精准时间范围，给搜索引擎提供完整检索配置。

### 一站式执行入口

```
auto_web_search_rewrite()
```

完整执行链路：需求识别 → 检索词改写 → 生成检索策略，返回全套检索配置；若无需联网直接返回静态标识。

### 输出字段结构（需要联网时）

```json
{
    "need_web_search": true,
    "search_reason": "需要联网的原因",
    "confidence": 0~1,
    "original_query": "原始提问",
    "rewritten_query": "适配搜索引擎的优化query",
    "search_keywords": ["关键词1","关键词2"],
    "search_intent": "检索意图描述",
    "suggested_sources": ["推荐网站类型"],
    "search_strategy": {
        "primary_keywords": ["核心词"],
        "extended_keywords": ["扩展同义词"],
        "search_platforms": ["推荐平台"],
        "time_range": "检索时间范围"
    }
}
```

## 5. 公共底层工具函数 `get_completion`

### 统一 LLM 调用封装，两个模块共用

1. **环境兼容**：检测 dashscope 库是否安装，未安装时本地模拟返回原始文本，无 API 报错；
2. **完整异常捕获**：捕获 HTTP 请求异常、状态码错误、空返回、无生成内容等各类接口异常；
3. **降级兜底**：任意异常直接返回原始 prompt，保证上层业务不中断；
4. **统一参数约束**：固定 temperature=0，保证输出稳定、无随机发散；
5. **返回统一文本结果**，上层自行做 JSON 截取解析。

## 7. 核心输出结构说明

1. 所有模型分析结果**强制 JSON 输出**，代码内置`find("{")`/`rfind("}")`截取纯 JSON 片段，过滤模型多余解释文字；
2. 所有 JSON 解析逻辑带 try-except 兜底，解析失败返回默认安全值，避免程序崩溃；
3. 置信度统一使用 0~1 浮点数，用于上层业务阈值判断（如置信度 > 0.8 才采用改写结果）。

## 8. 使用示例

### 示例 1：对话 Query 自动改写

```python
# 初始化对话改写器
rewriter = QueryRewriter()
history = """
用户:我想了解上海迪士尼疯狂动物城园区
AI:园区有朱迪训练营、警局
"""
query = "还有其他设施吗？"
res = rewriter.auto_rewrite_and_execute(query, conversation_history=history)
print(res["rewritten_query"])
# 输出：上海迪士尼疯狂动物城园区除朱迪警官训练营、警察局之外还有哪些游乐设施？
```

### 示例 2：联网检索预处理

```python
web_rewriter = WebSearchQueryRewriter()
query = "上海迪士尼今天人流量多吗，门票多少钱"
res = web_rewriter.auto_web_search_rewrite(query)
print(res["rewritten_query"])
# 输出：2026上海迪士尼乐园当日人流量实时情况及当日门票价格
```

## 9. 设计优势

1. **低耦合模块化**：对话改写、联网改写完全独立，可按需单独引入；
2. **高鲁棒性**：多层异常兜底，库缺失、API 故障、解析失败均不中断业务；
3. **标准化结构化输出**：统一 JSON 格式，便于下游检索 / 搜索引擎程序解析；
4. **场景专用 Prompt**：区分知识库检索、互联网检索两套优化逻辑，改写精准度更高；
5. **开箱即用**：内置完整 main 测试用例，无需额外开发即可验证效果；
6. **轻量化无额外依赖**：仅依赖 dashscope，无第三方复杂库。

# 离生产化的距离与实现

## 1. 现有代码当前存在的「Demo 级短板」（区分：逻辑缺陷 / 工程缺失）

### （1）架构与复用缺陷（最核心 Demo 特征）

1. 两份代码存在重复逻辑，完全没复用

   两段脚本各自实现一套 `get_completion`、各自处理 DashScope 导入 / 异常、JSON 截取逻辑，代码冗余严重；生产环境会抽离通用 LLM 客户端单例，全局共用。

2. 两个改写类完全隔离，无统一调度层

   真实 RAG 流程是：先对话消歧义改写 → 判断是否需要联网检索 → 联网 query 优化；现在两个类分开独立运行，无法串联流水线。

3. 模型硬编码写死在类内

   `qwen-turbo-latest`/`qwen-turbo`写死在函数参数，不支持动态切换模型、多模型负载均衡、本地大模型兼容（Ollama/Qwen 本地）。

### （2）鲁棒性薄弱，仅满足课堂演示

1. JSON 解析兜底非常粗糙

   仅简单截取{}，遇到模型输出换行、注释、多段 JSON、嵌套转义极易解析失败；无 JSON Schema 强校验。

2. 缺少请求限流、重试、超时控制

   DashScope 接口无超时、无指数退避重试、无并发锁；批量查询时极易触发 API 限流报错。

3. 无日志体系，无法排查问题

   仅 print 打印信息，没有分级日志（INFO/WARN/ERROR）、无请求 ID 落盘、无法记录原始 prompt、模型返回、改写前后 query 用于问题复盘。

4. 缺少参数可配置化

   API Key、模型名称、temperature、置信度阈值、搜索时间范围全部硬编码，不能通过配置文件 /env 统一管理。

### （3）业务能力缺失，仅覆盖基础案例

1. 无批量处理能力，仅支持单条 query

   线上 RAG 需要批量改写用户多轮 query、批量检索；当前仅单条调用。

2. 缺少过滤、去重、长度截断逻辑

   用户超长提问、无意义空 query、重复关键词没有预处理，直接丢给大模型浪费 token。

3. 缺少置信度阈值调度策略

   识别 query_type/need_web_search 返回 confidence，但代码没有分支逻辑：低置信度时降级、二次改写、走兜底规则检索。

4. 联网模块只做查询生成，没有真实搜索调用

   仅输出搜索策略、关键词，没有对接搜索引擎（百度 / 必应 / 百炼 WebSearch）、无结果解析、摘要整合逻辑，之前 404 报错就是缺失真实搜索链路。

### （4）工程交付缺失（线上必备，Demo 完全没有）

1. 无模块化分包结构，所有代码堆在一个文件
2. 无单元测试、集成测试用例
3. 无接口封装（FastAPI/Grpc），只能本地 Python 脚本运行，无法给前端 / 检索服务调用
4. 无缓存机制：相同对话历史 + query 重复请求会重复调用 LLM，浪费 token 成本
5. 无监控与指标：改写耗时、LLM 调用次数、联网检索占比、改写失败率无法统计

## 2. 距离生产可用的改造分层（三层，工作量清晰）

### 第一层：低成本改造（1 天完成，可直接用于内部测试环境）

目标：消除代码冗余、提升稳定性、统一调用逻辑

1. 抽离通用 LLM 客户端 `llm_client.py`

   统一封装 get_completion、密钥读取、超时、重试、状态码统一处理，两个改写类共用，删除重复代码；

2. 统一配置文件 `config.yaml`

   模型名称、置信度阈值、超时时间、搜索默认时间范围、API 密钥统一配置；

3. 完善 JSON 解析 + JSON Schema 校验

   使用`jsonschema`库约束模型输出格式，解析失败自动二次重试生成；

4. 增加基础日志 logging，替换所有 print 输出；

5. 串联双模块流水线：封装类，自动执行：`RagQueryPipeline`

   对话消歧义改写 → 判断是否需要联网 → 生成搜索关键词 / 策略

改造后效果：本地可完整跑通端到端 RAG 查询改写，稳定无崩溃，适合课程作业、实验室内部项目。

### 第二层：中等工程改造（2~3 天，可上线测试环境）

目标：具备线上基础服务能力

1. 增加缓存（Redis）：缓存相同 query + 对话历史的改写结果，降低 LLM 调用费用；
2. 封装 FastAPI 接口，提供 HTTP 服务，支持外部服务调用：
   - 单条 query 改写接口
   - 批量 query 改写接口
   - 完整 RAG 流水线接口（对话改写 + 联网识别 + 搜索策略输出）
3. 增加预处理过滤器：空文本过滤、超长文本截断、重复关键词清洗、特殊字符去除；
4. 置信度分支策略：confidence 低于阈值时，启用兜底规则模板改写，不依赖大模型；
5. 兼容本地大模型（Ollama），支持离线环境运行；
6. 补充单元测试：5 类对话 query、多组联网时效 query 自动化测试。

改造后效果：可作为独立微服务部署，供前端、知识库检索服务调用，并发、成本可控。

### 第三层：生产级强化（3~5 天，正式商用环境）

目标：高可用、可观测、合规、高性能

1. 限流、并发控制、异步接口（async FastAPI），支持高并发用户查询；
2. 完整监控指标：Prometheus 埋点，统计调用量、失败率、耗时、联网检索占比；
3. 对接真实搜索服务（阿里云百炼 WebSearch、第三方搜索 API），补全搜索结果拉取、摘要清洗、源文档输出；
4. 多模型路由：简单规则类查询用低成本轻量模型，复杂改写使用高精度模型；
5. 数据落盘：所有改写请求入库（MySQL），用于模型效果迭代、Bad Case 收集；
6. 异常告警：调用失败、接口限流自动推送告警；
7. 容器化 Docker 打包、K8s 部署配置、环境隔离；
8. 安全加固：密钥加密存储、入参校验防注入、输入脱敏。

## 3. 核心价值区分：Demo 原型 vs 生产服务

|   维度   |      当前 Demo 代码      |           生产可用改写服务           |

| 运行方式 |     本地脚本手动执行     |         后台常驻 HTTP 微服务         |
|  稳定性  | 无重试、无超时、解析易崩 |  多级异常兜底、自动重试、格式强校验  |
| 代码复用 |  大量重复 LLM 调用逻辑   |         统一客户端，分层解耦         |
| 串联能力 |  两个模块独立，无法联动  | 完整流水线，对话改写→联网判断一体化  |
| 并发能力 |   不支持多线程 / 批量    |        异步、批量、限流、缓存        |
| 可观测性 |       仅控制台打印       |    日志、监控、告警、请求数据存储    |
| 搜索能力 | 仅生成关键词，无真实检索 | 内置联网调用，返回网页摘要、来源链接 |
| 适配场景 |    课程演示、功能验证    |    企业 RAG、在线问答系统长期商用    |

## 4. 补充关键：底层算法逻辑无需大改

你现在两段代码**核心 Prompt 设计、query 分类逻辑、改写思路完全可以复用**，不需要推翻重写：

1. 5 类对话 query 分类逻辑合理，覆盖绝大多数用户口语问题；

2. 8 类联网检索识别规则贴合真实业务时效场景；

3. 搜索策略生成的分层设计（主关键词 / 扩展词 / 平台 / 时间）线上完全通用；

   所有改造都属于工程层优化，不是算法思路重构，改造成本很低。
