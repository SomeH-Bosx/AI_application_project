# 向量数据库与元数据管理实战

## 版本一

**基于 LangChain + 阿里 DashScope 通义大模型 + FAISS 向量库**的 PDF 文档 RAG 检索问答系统，专门读取银行考核制度 PDF，提问后返回答案并标注答案来源 PDF 页码

完整流程：

PDF 读取 → 全文提取 + 记录每页文本对应页码 → 文本切块 → 向量嵌入构建 FAISS 库（持久化保存）→ 问题相似度检索 → 大模型基于匹配文本回答 → 输出答案 + 来源页码。


**==Q：这个项目中元数据是怎么被管理的？==**

这段代码**完全自定义实现元数据管理**，没有使用 LangChain FAISS 标准`Document.metadata`，而是自建一套独立映射体系：

- 用字典 `page_info: {文本块: 页码}` 存储元数据（页码）；
- 用`pickle`序列化单独保存到`page_info.pkl`文件，和 FAISS 向量索引文件分离；
- 挂载到 FAISS 对象自定义属性 `.page_info` 全局携带，检索时通过文本块反向匹配页码。

这种属于**外置独立元数据存储方案**，和 Redis、SQLite 外置元数据逻辑同源，只是用本地文件替代数据库。



## 版本二

思路完全与版本一相同，实现方式有所不同。

## 两者差异

### 共性

两段代码底层链路完全一致：PDF 读取→文本分块→DashScope 向量化→FAISS 向量库持久化→检索问答 + 页码溯源；依赖完全相同的 API、存储方案、加载逻辑，仅在**页码映射方案、LLM 调用链路、工程细节、检索参数**四大维度存在本质差异。

### 一、核心模块逐项对比

#### 1. PDF 页码映射（最关键，决定溯源准确率）

##### 第一段：行级文本匹配方案

1. 存储结构：`page_numbers = [页码]`，按换行切割文本，**一行绑定一个页码**
2. 定位逻辑：
   - 用`text.find(chunk前100字符)`全局字符串匹配找 chunk 起始位置
   - 统计起始位置前换行数量，取对应行的页码作为 chunk 来源
   - 多重兜底模糊匹配，匹配失败直接赋值`-1（未知页）`
3. 致命缺陷：
   - 字符串`find()`极易匹配到文档重复文本，定位偏移
   - chunk 存在`chunk_overlap`跨多行、跨页面时，只能取单行页码，丢失多页信息
   - 无换行长段落、表格文本会完全匹配失败，大量输出 “未知页码”
   - 匹配逻辑多层 if 嵌套，容错逻辑复杂，维护成本高
4. 优势：内存占用更低，小 PDF 性能微弱领先

##### 第二段：全局字符偏移映射方案（工业级精准方案）

1. 存储结构：`char_page_mapping = [每个字符对应的页码]`，全文每一个字符绑定所属页码
2. 定位逻辑（无字符串查找，零误差）：
   - 全局游标`current_pos`顺序遍历所有 chunk，记录每个 chunk 的字符起止下标
   - 切片取出该 chunk 全部字符对应的页码列表，统计**众数（出现最多页码）** 作为该块归属页
   - 游标直接偏移至 chunk 末尾，顺序严格对齐文本分割流程
3. 优势：
   - 100% 无匹配失败，不存在`未知页码`；跨页 chunk 能精准识别主要页面
   - 不受换行、段落、表格、重复文本干扰，适配所有排版 PDF（银行制度 / 合同 / 报表）
   - 逻辑线性简单，无复杂模糊匹配，稳定易维护
4. 微小缺点：超大 PDF 会占用少量额外内存存储字符映射数组

|     对比项      |    第一段（行匹配）     | 第二段（字符偏移） | 生产推荐 |
| :-------------: | :---------------------: | :----------------: | :------: |
|   溯源准确率    |     低，大量未知页      |    极高，零丢失    |  第二段  |
| 跨页 chunk 处理 |    仅单页，丢失信息     |    识别主要页码    |  第二段  |
| 复杂 PDF 兼容性 | 差（无换行 / 多栏失效） |  完美兼容各类 PDF  |  第二段  |
| 代码维护复杂度  |    高，多层兜底判断     |    低，线性遍历    |  第二段  |
|    内存开销     |          更小           |    略高，可忽略    |  无影响  |

#### 2. 文本分割器与导入规范

1. 分割器配置：

   两段完全一致

   ```python
   separators=["\n\n", "\n", ".", " ", "", "。", "？", "！"]
   ```

   均包含中英文标点，对中文制度文档友好。

2. 导入路径差异（LangChain 版本规范）

   - 第一段：`from langchain.text_splitter import RecursiveCharacterTextSplitter`（旧社区包导入，新版会出现弃用警告）
   - 第二段：`from langchain_text_splitters import RecursiveCharacterTextSplitter`（官方新版独立分包，标准推荐写法，无版本警告）LangChain

3. 空页日志：第二段增加`No text found on page x`打印，调试友好；第一段无空页提示。

#### 3. LLM 问答执行链路（最大工程化差异）

##### 第一段：LangChain 标准 QA 链 `load_qa_chain(chain_type="stuff")`

1. 封装能力：

   - LangChain 内置标准文档拼接逻辑，自带规范 Prompt 模板，自动处理多文档上下文
   - 支持`get_openai_callback`自动统计 token 消耗、API 计费，便于成本管控
   - 标准化输入输出结构，可无缝切换`stuff/map_reduce/refine`多种问答策略

2. 检索参数：

   ```
   similarity_search(k=2)
   ```

   ，仅召回 2 个最相关文本块

   - 优点：上下文短，减少无关噪声，降低 token 消耗、避免上下文溢出
   - 缺点：极长文档时可能丢失关键信息

3. 适用场景：标准化 RAG 系统、需要统计 API 成本、轻量化问答

##### 第二段：手动拼接 Prompt，原生`llm.invoke()`裸调用

1. 特性：
   - 完全手动拼接上下文 + 问题，无 LangChain 内置封装，Prompt 自定义自由度极高
   - **无 token 计费统计**，无法自动追踪 API 消耗，需要自己实现统计逻辑
   - 检索参数：`similarity_search(k=10)`，一次性拉取 10 个文本块
2. 缺陷：
   - 10 个 chunk 拼接上下文过长，极易混入大量无关文本，模型干扰、幻觉增多
   - 长上下文会显著增加 token 费用，甚至触发 LLM 上下文长度限制报错
   - 无标准化输出结构，多轮问答、溯源扩展需要手动编写大量字符串处理代码
3. 适用场景：临时调试、高度自定义 Prompt、不需要长期成本监控的小工具

#### 4. 其他细节差异

1. 类型注解笔误：第二段函数返回注释`List[Tuple[str, int]]`为错误，实际是`List[int]`，第一段注解准确。
2. 日志输出：第二段新增`页码映射完成，共xx个文本块`日志，预处理进度可视化更好。
3. 代码注释：第二段存在 jupyter 单元格标记`# In[9]:`，正式工程需删除；第一段无冗余标记。
4. 页码读取容错：两段读取`page_info`逻辑完全一致，均兼容向量库加载后的溯源打印。

### 二、两段代码各自优缺点总结

#### 第一段优点

1. LangChain 标准 QA 链，自带成本统计回调，工程标准化
2. 检索 top_k=2，上下文精简，token 成本更低、回答干扰少
3. 行级映射内存占用更小，极小 PDF 处理速度略快

#### 第一段致命短板

1. 页码溯源逻辑不稳定，大量场景匹配失败，业务文档溯源不可信
2. 旧版分割器导入，高版本 LangChain 会抛出弃用警告
3. 模糊匹配多层嵌套代码，后期难以维护迭代

#### 第二段优点

1. **字符偏移页码映射，溯源精准无丢失，企业业务文档刚需**
2. LangChain 新版标准导入，无版本兼容警告
3. 分割、页码映射流程线性简洁，调试日志完善
4. Prompt 完全自定义，灵活调整回答约束（如禁止幻觉、强制引用原文）

#### 第二段短板

1. 裸调用 LLM，无内置 API 计费统计，成本监控需额外开发
2. top_k=10 召回过多文档，上下文冗余，易产生幻觉、增加费用
3. 无封装 QA 链，多轮对话、复杂问答策略扩展工作量大

### 三、适用场景推荐

#### 场景 1：快速测试、极简工具、超短 PDF（≤10 页）

选择**第一段**：轻量化、成本自动统计，排版简单的文档溯源误差可接受。

#### 场景 2：企业正式系统、银行制度 / 合同 / 报表、要求精准页码溯源（生产环境）

优先**第二段主体逻辑**，做两处优化融合第一段优势：

1. 检索 k 值改为 3~5，平衡召回完整性与上下文噪声
2. 替换裸调用为`load_qa_chain`标准链，接入`get_openai_callback`统计费用
3. 保留字符偏移精准页码映射（核心）
